# Architecture Decision Records — v0.2

결정된 제품 요구사항은 `URS.md`, 상세 구현 결과는 Spec/Issue/PR에서 관리한다.

## ADR-001 — Tauri 2 + Rust 데스크톱 앱 (Accepted, 2026-11-18)
- **결정:** Electron 대신 Tauri 2, Rust 네이티브 로직, React+TypeScript UI 사용.
- **이유:** Windows/macOS 지원, 웹 UI 재사용, OS WebView 활용으로 Chromium 별도 번들 부담 축소 기대, Rust를 실제 제품에서 학습·적용하는 개인 프로젝트 목적.
- **대안:** Electron/TypeScript 단일 스택. 생태계 및 UI 일관성/학습 비용 장점이 있으나 별도 Chromium 패키징 부담.
- **트레이드오프:** WebView2/WKWebView 차이, Rust 러닝커브, 네이티브 의존성 빌드와 서명, JS↔Rust IPC 계약 설계.
- **검증:** 두 OS에서 앱 실행·저장/알림·릴리스 빌드; 설치 크기, 기동 시간, 유휴 메모리는 실측. **Tauri가 항상 더 빠르다는 가정은 하지 않는다.**

## ADR-002 — SQLite 로컬 RDBMS (Accepted direction, schema pending)
- **결정:** 앱 데이터는 로컬 SQLite 사용. 관계형 엔터티(공고, 출처, 근거, 지원, 전형, 파일)를 SQL 관계로 관리.
- **이유:** 별도 DB 서버 없이 단일 사용자 PC에서 트랜잭션과 JOIN을 활용. 사용자 경험은 MySQL이지만 저장·운영 모델은 로컬 앱에 맞춤.
- **주의:** NoSQL이 '실시간으로 빨라야 할 때 쓰는 DB'라는 전제는 잘못이다. 선택 기준은 데이터 모델·일관성·배포 운영 요구다.
- **미정:** 마이그레이션/스키마/FTS/암호화 및 파일 저장 정책.

## ADR-003 — 로컬 데이터 기본, 모델 공급자는 사용자가 준비 (Accepted)
- **결정:** 사용자 영구 데이터 저장은 PC 내부. 필요한 부분만 외부 JD 링크 또는 사용자가 선택한 LLM에 송신. 모델 계정/API 키는 사용자가 제공.
- **대안:** 중앙 서버에 사용자 데이터를 저장하는 SaaS형 서비스 — 개인정보/운영 비용/동기화 요구가 없어 채택하지 않음.
- **주의:** 클라우드 API 요청은 데이터 전송이므로 '완전 오프라인/데이터가 외부로 나가지 않는다'고 표현하지 않는다.

## ADR-004 — Public GitHub + 사람이 관리하는 PR (Accepted)
- **결정:** Issue → feature branch → Codex 구현 및 테스트 → PR → 사용자 검토 → 직접 Merge. `main` 직접 수정/자동 Merge 금지.
- **CI/CD:** PR 품질 검사, 마일스톤 태그에서 Windows/macOS 설치 파일 빌드와 Releases 게시.
- **주의:** 1인 리포지터리에서 자체 승인만으로 GitHub의 필수 리뷰 규칙을 만족한다는 보장은 없다. CI/브랜치 보호와 리뷰 체크리스트를 구분한다.

## ADR-005 — 외부 채용 사이트 자동 제출 제외 (Accepted, 2026-11-18)
- **결정:** 사용자가 실제로 제출한다. 앱은 자료 묶음/링크/복사 인터페이스를 제공하고 제출 이후 수동 완료 기록과 제출 PDF 보관만 담당.
- **이유:** 클라이언트가 요구한 정확한 책임 범위, 플랫폼별 로그인/약관/양식 차이 회피.
- **영향:** 옛 `Submission Adapter`와 '승인 후 자동 제출' 요구사항 제거. 제출 링크 클릭은 지원 완료가 아니다.

## ADR-006 — 단계별 문서 검색 (Proposed)
- **제안:** 초기에는 SQLite FTS5 검색과 근거 메타데이터로 검증 가능한 분석/생성 세로 흐름을 만들고, 정확도 평가 후 임베딩·하이브리드 검색 도입 여부 결정.
- **주의:** 검색 기반 생성이 RAG인지 여부는 근거 검색과 생성 분리, 출처 추적 능력으로 확인할 것. 벡터 DB를 처음부터 필수라고 가정하지 않음.

## ADR-007 — 릴리스/업데이트 UX (Accepted intent / details pending)
- **결정:** 마일스톤별 Windows/macOS 설치본을 Releases로 게시. 신규 버전 알림은 제공하되 설치는 사용자가 선택.
- **미정:** 최초 지원 아키텍처(Apple Silicon/Intel), 코드 서명/공증, 자동 업데이트가 아닌 외부 다운로드 방식, GitHub API 접근 정책.

## ADR-008 — 알림과 백그라운드 동작 (Proposed)
- **제안:** 장시간 앱 실행, 시스템 트레이/메뉴 막대, 로그인 자동 시작 옵션, 매일 아침 OS 알림, 놓친 알림은 다음 실행에서 확인.
- **미정:** 앱 완전 종료 상태에서 보장 범위, OS 권한, 표시 시간/빈도. 확인 전에는 동작 보장하지 않음.

## ADR-009 — 최초 통합 프로토타입과 분야 중심 정렬 (Accepted scope, details pending)
- **사용자 확정:** 최초 릴리스에 메일/JD 분석, 맞춤 지원서·자체 문항 작성, 독립 AI 리뷰·사용자 승인, 직접 제출 보조, PDF·전형·아침 알림 관리까지 포함한다. 내부 단계는 작은 구현/PR 단위이며 출시 범위를 줄이는 기준이 아니다.
- **정렬:** 사용자가 선택한 분야와 JD의 연관성이 높은 공고 우선. 필수 자격과 개인 경험 평가를 별도로 제공한다. 별도 개인 선호 입력·평가는 최초 릴리스에서 제외한다.
- **실행 계획:** Provider는 M0 Mock 계약과 M1 최초 실제 연결로 앞당겨 분석·평가·생성·리뷰가 공유한다. 최초 공급자/모델과 작업별 계약은 해당 구현 전에 검토한다.
- **미정:** 동점·미분석·필수 자격 미충족 공고의 위치, 분야 선택 UI, 실제 AI 평가 합격 기준. 모든 상세 Spec을 일괄 승인한 것으로 취급하지 않는다.
